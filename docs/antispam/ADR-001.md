# Contact antispam — decision and remaining release gates

EPIC #64; foundation #65. Frozen initial base: `2878726ba4ae7d7618ab4f3b42c22667a19bb5a5`.
Manual session. Integration target: `epic/64-antispam-contact`.

## Decision

Keep Astro static and the PHP endpoint on OVH. Pin the MIT-licensed ALTCHA widget
3.5.0 and PHP library 2.3.0, using protocol v2 and PBKDF2/SHA-256. Composer and npm
lockfiles are authoritative. A server secret signs the challenge; the fast
verification key is derived with a separate HMAC context. Never accept unsigned
or non-expiring challenges. No CAPTCHA provider request, profiling, cookie or
third-party script is required.

Use PDO SQLite exclusively for this first implementation: atomic transactions
provide single-use proofs and shared quotas across PHP workers. No unverified
filesystem fallback. Database, app, Composer dependencies and config live outside
the document root. Fail closed on missing config/secret, full/unavailable database
or unsupported runtime. A contact e-mail and phone remain available on the page.

The existing honeypot stays. Size/type validation, rate limits and mail-failure
diagnostics implement the necessary #16 interface in this EPIC without moving
that issue from parent #12 or changing any admitted mission.

## Parameters to calibrate

20-minute TTL; 20 challenge attempts and 5 POST attempts per 10 minutes/IP.
Global initial caps: 200 challenges and 100 POSTs per 10 minutes. Quotas count
attempts, including invalid submissions. Use only REMOTE_ADDR (never trust
client-supplied Forwarded/X-Forwarded-For). A trusted reverse-proxy deployment
requires an explicit reviewed adaptation; do not enable it by changing headers.
IP keys are HMACs scoped by day and endpoint; keep no raw IP, contact data or
user agent in the database. Counters expire in 10 minutes; used-proof identifiers
expire with their challenge. Purge on bounded writes. Persist across restarts.

32 KiB request body, 10,000 message characters, fixed maximum field sizes and
allowlisted request type/budget. A new challenge is needed after a consumed
proof, including mail failure. Claim at most one mail adapter invocation per
proof, never exactly-once SMTP delivery.

PoW defaults (5000 PBKDF2 iterations, randomized counter 500–1000) are provisional.
Target: mobile p95 at most 3 s, PHP verification p95 at most 100 ms. The package
has changed protocols/API: future upgrades require cross-language fixtures and
browser tests, not a range-only version bump.

## Evidence and unresolved prerequisites

Local tooling: PHP 8.5.12 (portable official archive, SHA-256 checked) and Composer
2.11.0, isolated under the operator's temporary tools directory. Tests do not
prove OVH compatibility. No OVH shell/credentials were provided in this session.

Before production, run the bundled CLI preflight on the actual hosting runtime;
confirm PHP >=8.1 with PDO SQLite/mbstring, writable private storage, effective
multi-process transactions, correct document root and successful mail reception.
A reverse-proxy IP mapping and global budget must be reviewed on that host.
Measure on a reference modest phone and validate keyboard/screen reader manually.
No measured spam-reduction or WCAG-conformance claim is made.

## Release/rollback boundary

Do not deploy the new frontend with an old unprotected endpoint. Package private
app and public site together; retain state/config between releases. Roll back to
a known protected version or disable submission with alternative contact.
Record J+1/J+7 observations before closing the EPIC. Keep #65 open until actual
hosting and mobile evidence exists, even when the local implementation is ready.
